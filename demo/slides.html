guidemd

Executable, dimension-aware guides for llm-d

One source of truth per guide →

  • an interactive page on llm-d.ai — pick your configuration, read only your steps
  • a readable GitHub copy with pre-rendered, CI-tested variants
  • an executable CI run derived per configuration — docs and CI can't drift

Requirements first, then three proof-of-concepts. (→ / ← to navigate)

Background — today's pain points

  • Readers: monolithic guides covering many dimensions (infra, accelerator, model server…) distract users focused on one configuration — and answering "can I run PD disaggregation with RDMA on TPU using SGLang?" or finding its test results is hard
  • Writers: large duplicated sections (router install, verification…) drift apart over time; no structured way to add dimension-specific content (e.g. a model streamer for GKE TPU) without cluttering every other config
  • CI: no defined contract between guide and pipeline — "magical parsing" of READMEs breaks on guide edits and gets patched by hand

Requirements

P0 = required · P1 = highly desirable, negotiable

Guide readers P0 interactive, contextual guide on llm-d.ai — select a configuration, see curated applicable content; the same configuration links to test status, benchmark results, known issues
P1 readable guide format on GitHub / local editors
Guide writers P0 structured mechanism for dimension-specific content without noise in irrelevant configurations
P1 common sections maintained once, imported as needed
llm-d CI P0 automatically derive executable, verifiable runs for any supported combination — no drift between docs and CI
P1 affordable on every PR: default dry-runs; full e2e per matrix cell on a schedule / on demand

Non-goals: changing the llm-d installation process (solution is agnostic to it) · highly customized installs — the focus is out-of-the-box well-lit-path recipes with minimal customization.

Design principles

1 · Single source of truth. No forks per dimension value, no parallel documentation tracks.
2 · Automated generation. Readers and CI consume derived artifacts; a validate gate blocks PRs on drift.
3 · CI as a standard user. CI executes guide steps sequentially, interpreting no custom semantics.
4 · Structured guide dimensions. Owners author branches in isolation; readers get a distraction-free contextual guide; CI configuration is auto-generated. All supported and CI-validated configurations are declarative.
5 · Composition over duplication. Shared sections are imported fragments with parameters.

Design space — three PoCs, none perfect

  • pr1988-guide-yaml (baseline) — the upstream proposal (llm-d#1988): bash steps in guide.yaml, README rendered from a template
  • annotated-markdown — one plain-markdown guide with invisible comment directives (when / import / step); a bespoke compiler projects variants and CI plans
  • jinja-markdown — one Jinja2 template + guide.yaml; inline {% step %} blocks; no document parser owned at all

The two successors keep everything #1988 got right (derived docs, CI gate, incremental adoption) and add the dimensions/rules/ci matrix. A parity suite proves they describe the SAME guide: identical matrices and per-cell step counts across 96 variants × 3 plan flavors.

Inside jinja-markdown — the authoring model

{% if model_server in ["vllm", "sglang"] %}          conditionals over anything
{% step group="router-values" %}                     inline executable step —
export ROUTER_VALUES="-f ${REPO_ROOT}/guides/…"      rendered as a bash fence
{% endstep %}                                        AND recorded for the plan
{% endif %}

{% include "prereqs.md.j2" %}                        shared sections, once

{{ configure_step() }}                               generated: your picks as
                                                     env vars (${ACCELERATOR}…)

Steps live inline in the narrative. Dimension picks become environment variables via one generated step, so bodies stay plain, copy-pasteable shell. Groups + {% else %} + StrictUndefined + bash -n catch coverage gaps, typos and syntax errors at validate time.

The user journey

WRITE                 edit guide.md.j2 / guide.yaml / common/*.md.j2
  │
PREVIEW & CHECK       guidegen.py render <guide> --set accelerator=tpu/v6
  │                   guidegen.py validate <guide>
  │
REGENERATE & COMMIT   guidegen.py render-md <guide>
  │                   readonly-guide.md + variants/ for CI-tested cells
  │
PR GATE (CI)          validate + cluster-free dry-run per matrix cell
  │ merge
  ├── NIGHTLY CI      matrix --github → per cell: e2e plan | bash
  └── WEBSITE BUILD   emit-docusaurus at the release tag → llm-d.ai

End-to-end surfaces

  • Website: dropdowns in dimension order (invalid combos unselectable); each variant is its own static page — search/SEO/no-JS safe, deep-linkable; ✓ CI-tested / ⚠ supported badge per pick
  • GitHub / local: default doc opens with a configuration table — CI-tested rows link to pre-rendered variant guides; the long tail points to the website or render --set
  • CI: matrix --github emits the job matrix; each job runs plan --set … --skip ci=skip --skip dry-run=skip | bash (every PR, zero credentials) or the e2e flavor nightly — asserted verification, stable step ids, file:line provenance in every log line
